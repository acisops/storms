# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

`storms` is a solar storm analysis package for ACIS Ops, used to monitor space weather (ACE particle flux, GOES proton flux, HRC shield proxy, ACIS "txings" threshold-crossing rates) for the Chandra X-ray Observatory's ACIS instrument, and to write storm memos / calculate radiation fluence avoided by SCS-107 safing actions.

- Core class: `storms.solar_wind.SolarWind` (`storms/solar_wind.py`) — data ingestion + plotting.
- CLI apps (`storms/apps/`): `calc_p3_fluence` (ACE P3 fluence avoided) and `make_storm_plots` (generates a storm-memo plot set from a YAML params file — see `doc/source/command_line.rst` for usage and a sample config).
- `storms/txings_proxy/` — ML models (torch/sklearn) predicting txings rates as a GOES/HRC proxy; `Models/`, `Indices/`, `Plots/` hold pretrained artifacts, not regenerated by any build step.
- `dev/` and `scripts/` hold exploratory notebooks/scripts, not part of the installed package.

## Environment requirement

This package depends on the internal Chandra "Ska" ecosystem (`cheta`, `kadi`, `acispy`, `ska_numpy`, `ska_path`, `ska_helpers`, `cxotime`), which is not on PyPI. It only imports/runs inside the ACIS Ops Ska Python stack, activated via the `acisska` alias (`conda activate ska`, `SKA=/proj/sot/ska`). `setup.py`'s `install_requires` is stale/incomplete — don't rely on it to determine actual dependencies; check imports in the code instead.

Data paths are hardcoded to the ACIS ops filesystem, not configurable via env vars:
- ACE: `/data/acis/ace`
- GOES: `/data/acis/goes` (specifically `/data/acis/goes/goes_16_18.fits`)
- txings: `/data/acis/txings`
- HRC shield: via `ska_path("data", "arc")` → `hrc_shield.h5`

Code that touches these paths only works on a host with this data mounted.

## Lint and format

Formatting/linting is via `ruff` (config in `ruff.toml`, extending `ruff-base.toml`; `pre-commit` also runs it). CI (`.github/workflows/`) checks both and will fail the build on violations:

```
ruff format --check
ruff check
```

Run `ruff format` and `ruff check --fix` before committing.

## Testing / verification

There is no automated test suite. Verify changes by a combination of: exploratory notebooks (`dev/`, `scripts/`) for quick checks, and a manual run of the relevant CLI app or `SolarWind` method against real data on the ACIS ops filesystem (inside the activated Ska stack) before considering a change done.

## Git workflow

Commits go directly to `main` — no feature-branch/PR convention in this repo. Commit messages are short, informal, imperative-present-tense subject lines with no body text and no conventional-commit prefixes (e.g. "Fix limits", "add descriptions").

## Docs

Sphinx docs live under `doc/`, built with `make html` from inside `doc/` (`sphinx-build -M <target> source build`). `doc/build/` (prebuilt HTML) is committed — rebuild and re-commit it when docs source changes, to avoid stale committed output.
